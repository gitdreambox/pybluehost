# PyBlueHost v1.2 PTS IUT — Design Spec

**版本**：v1.2（Phase 1 + Phase 2）
**日期**：2026-05-31
**对应 PRD**：[docs/PRD-v1.2.md](../../PRD-v1.2.md)
**状态**：设计草案（待评审 → writing-plans）

> 本 spec 覆盖 **Phase 1**（Fluoride 式 PTS mode + 交互式控制台手动驱动 + PICS 半自动生成，§1-11）和 **Phase 2**（auto-pts BTP 自动化，§12）。
> - **Phase 1** 是 v1.2 主体交付（4 Plan，~7.5-8.5 周），可独立完成 + 验收
> - **Phase 2** 在 Phase 1 之上自然延伸（复用 action layer + PTS mode flags），单独排期；其设计预先在本 spec 落地以保证 Phase 1 接口前向兼容

---

## 0. 目标一句话

让 PyBlueHost 当 IUT 跑 SIG PTS 一致性测试：①加一组 **PTS mode 配置 flags** 调整栈行为使其可测；②加一个 **IUT action layer** 把"驱动栈"抽成原语，外加 **交互式 REPL 前端** `pybluehost app pts-iut` 供操作员随 PTS MMI 提示手动驱动；③加一个 **PICS 半自动生成器** 从栈能力出 PICS 草稿。

## 1. 与现有代码的接点（已核对）

| 接点 | 现状（已读源码确认） |
|---|---|
| Stack 顶层 API | `stack.py` — `connect_gatt()` **→ 返回 `GATTClient`**（绑定 conn handle，central 角色）、`connect_classic()` **→ 返回 int ACL handle**、`authenticate_classic()` `pair(handle)` `encrypt(handle)` `enable_classic_encryption()`；句柄访问器 `gap()` `gatt_server()` `sdp()` `rfcomm()` `l2cap()` `smp()` `hci()` `trace()` `local_address` `is_powered` |

| GATT client（central 角色）| `ble/gatt.py:434 GATTClient` — `read_characteristic(handle)` / `write_characteristic(handle,value)` / `discover_all_services()` / `discover_characteristics()` / `discover_descriptors()`（由 `connect_gatt` 返回） |
| GAP（Classic）| `classic/gap.py` — `start(InquiryConfig)` `set_discoverable` `set_connectable` `set_extended_inquiry_response` `connect(addr)` `disconnect(handle)` |
| SDP | `classic/sdp.py:484 search(target,uuid)` / `:495 search_attributes(...)` |
| RFCOMM | `classic/rfcomm.py:403 connect(acl_handle, server_channel)` / `:192 open_dlc(channel)` |

| StackConfig | `stack.py:27` — `le_io_capability` `classic_io_capability` `security:SecurityConfig` `trace_sinks` `bondable` 等；**PTS mode flags 加这里** |

**关键现实校正**：当前栈**没有**自动发起 LE Connection Parameter Update（grep 无 sender）。因此 `pts_disable_conn_updates` 在 v1.2 是**防御性 guard**（语义占位 + 若未来 profile 加了自动 update 则尊重此 flag），不是修复现有行为。spec 如实标注，避免假装修了不存在的行为。

## 2. 架构总览

```
                          pybluehost app pts-iut  (REPL 前端)
操作员 ──敲命令──►  ┌──────────────────────────────────────┐
                  │ REPL loop                            │
PTS MMI 提示 ─────►│  - 读 stdin（run_in_executor，不阻塞   │
（人看人转述）      │    event loop → 异步栈事件照常处理）   │
                  │  - 解析命令行 → 调 action layer        │
                  └──────────────────┬───────────────────┘
                                     ▼
                  ┌──────────────────────────────────────┐
   Phase 2 BTP ──►│ IUT action layer  (IutActions)       │  ← 共享原语，无前端耦合
   tester (后续)   │  advertise/scan/connect/disconnect/   │
                  │  pair/encrypt/notify/indicate/read/   │
                  │  write/sdp-browse/rfcomm-open/        │
                  │  l2cap-connect/set-io-cap/status      │
                  │  + 会话状态（连接表/last handle/io cap）│
                  └──────────────────┬───────────────────┘
                                     ▼
                  ┌──────────────────────────────────────┐
                  │ Stack  (PTS mode flags 生效)          │
                  │  StackConfig.pts: PTSModeConfig|None  │
                  │   - None(默认) → 零行为变化           │
                  │   - 开 → secure-only / 抑制 update /  │
                  │     SMP options 覆盖 / SMP 失败注入 / │
                  │     LE pair 后不自动 SDP              │
                  └──────────────────────────────────────┘
```

**三块解耦**：
- **PTS mode flags**：纯配置 + 栈内 hook，opt-in，默认零影响。可独立单测（开 flag → 断言行为变化）。
- **action layer (`IutActions`)**：无 REPL / BTP 耦合，Phase 2 BTP tester 复用同一层。
- **REPL 前端**：只做"行 → action 调用 + 打印结果"，薄。

## 3. PTS mode flags 设计

新增 `PTSModeConfig` dataclass（独立文件 `pybluehost/pts/config.py`），挂到 `StackConfig`：

```python
@dataclass
class PTSModeConfig:
    disable_conn_updates: bool = False      # 抑制 LE 连接参数自动更新（防御 guard，见 §1）
    secure_pair_only: bool = False          # 强制 SC-only 配对，拒 legacy
    disable_sdp_on_le_pair: bool = False    # LE pair 完成后不自动触发 SDP/CTKD-classic
    smp_options: bytes | None = None        # 覆盖 SMP 配对选项原始字节（io_cap/auth_req/key dist）
    smp_failure_at: str | None = None       # 在指定阶段注入 Pairing Failed（异常路径 test case）

# StackConfig 增一字段（默认 None = PTS mode 关，零行为变化）：
#   pts: PTSModeConfig | None = None
```

| Flag | Hook 位置 | 行为 |
|---|---|---|
| `disable_conn_updates` | 任何自动发起 LE conn param update 的点（当前无 → guard） | 该点检查 flag，开则不发 |
| `secure_pair_only` | SMP 配对特征交换（`ble/smp.py`）+ 复用 `SecurityConfig` 既有 `sc_only_mode` stub 语义 | 强制 SC bit，对端不支持 SC 则 Pairing Failed |
| `disable_sdp_on_le_pair` | LE 配对完成回调里触发 SDP/CTKD-classic 的点 | 开则跳过自动 SDP |
| `smp_options` | SMP Pairing Request/Response 构造处 | 用给定字节覆盖 io_cap/auth_req/max_key/key dist |
| `smp_failure_at` | SMP 状态机各阶段 | 到指定阶段主动发 `SMPPairingFailed`（reason 可配） |

**强约束**：`pts=None` 时所有 hook 短路，行为与 v1.1 完全一致。每个 flag 配独立单测（loopback 两端，开 flag 断言行为）。`smp_options` / `secure_pair_only` 互动经 `_validate_sc_dependencies` 同款校验扩展。

**`secure_pair_only` 与 `SecurityConfig.sc_only_mode` 的接线**：单点接线——`Stack._build` 时若 `config.pts and config.pts.secure_pair_only`，则自动设 `config.security.sc_only_mode = True`（覆盖默认 False）。SMP 代码只查 `SecurityConfig.sc_only_mode`，无须感知 `PTSModeConfig`。这样：
- v1.0 SMP 测试不变（pts=None 时 sc_only_mode 仍是默认值）
- v1.2 PTS mode 通过单点 build-time 转译生效
- 未来其它需要 sc_only_mode 的场景（非 PTS）可直接设 `security.sc_only_mode=True`，路径统一

## 4. IUT action layer 设计

`pybluehost/pts/actions.py` — `IutActions`，持有 `Stack` + 会话状态：

```python
@dataclass
class ConnInfo:
    handle: int                          # ACL/conn handle
    peer: BDAddress
    transport: str                       # "le" | "classic"
    gatt_client: "GATTClient | None"     # central 出向连接才有（connect_gatt 返回）

@dataclass
class IutSession:
    connections: dict[int, ConnInfo]     # handle → ConnInfo（出向 + incoming 都登记）
    last_handle: int | None              # 最近一次连接，命令省略 handle 时用
    le_io_capability: int                # set-io-cap 改的当前值
    classic_io_capability: int

class IutActions:
    def __init__(self, stack: Stack) -> None: ...

    # —— 动作原语（每个映射到 Stack API）——
    async def advertise(self, *, adv_type=..., data=...) -> None       # stack.gap.ble_advertiser.start(cfg, ad_data=)
    async def scan(self, *, active=False) -> None                      # stack.gap.ble_scanner.start() + on_result
    async def connect(self, addr: BDAddress, *, le=True) -> int        # le: connect_gatt()→GATTClient(存 ConnInfo)；classic: connect_classic()→handle
    async def disconnect(self, handle: int | None = None) -> None
    async def pair(self, handle=None, *, io_cap=None, mitm=False) -> None   # stack.pair(handle)
    async def encrypt(self, handle=None) -> None                       # stack.encrypt / enable_classic_encryption
    # peripheral 角色（IUT 当 GATT server）：
    async def notify(self, char_handle: int, value: bytes, handle=None) -> None    # stack.gatt_server.notify
    async def indicate(self, char_handle: int, value: bytes, handle=None) -> None  # stack.gatt_server.indicate
    # central 角色（IUT 当 GATT client，需该连接的 GATTClient）：
    async def read(self, char_handle: int, handle=None) -> bytes       # ConnInfo.gatt_client.read_characteristic
    async def write(self, char_handle: int, value: bytes, handle=None) -> None     # .write_characteristic
    async def sdp_browse(self, addr: BDAddress, *, uuid=None) -> list   # sdp().search/search_attributes
    async def rfcomm_open(self, addr: BDAddress, channel: int) -> None  # connect_classic → rfcomm().connect(handle, channel)
    async def l2cap_connect(self, addr: BDAddress, psm: int) -> None    # l2cap()
    def set_io_cap(self, cap: str) -> None                             # 改会话 io cap，下次 pair 生效
    def status(self) -> IutSession                                     # 当前状态快照
```

**设计要点**：
- **角色区分**：`read`/`write` 是 central 角色（用 `connect_gatt` 返回的 `GATTClient`，存在 `ConnInfo.gatt_client`）；`notify`/`indicate` 是 peripheral 角色（用 `stack.gatt_server` + incoming conn handle）。PTS 不同 test case 测不同角色，session 两类连接都登记。`read`/`write` 时若该 `ConnInfo` 无 `gatt_client` → `error: not a central connection`。
- `handle=None` → 用 `session.last_handle`（操作员少敲 handle，MMI 提示多是"在当前连接上做 X"）。
- action 返回值/异常由前端格式化；action layer 不打印。
- 会话状态跨命令保持（这就是 REPL 常驻 + 同一 `IutActions` 实例的意义）。
- 注册 `stack.on_connection_event` → incoming 连接/断开自动登记进 `session.connections`（这类无 `gatt_client`，是 peripheral 侧）。

## 5. REPL 前端设计

`pybluehost/cli/app/pts_iut.py` + `pybluehost/pts/repl.py`：

- 命令注册：`register_pts_iut_command(subparsers)` 加 `pts-iut` 子命令（带 `-t/--transport` + trace flags，复用 `add_common_arguments`）。
- 启动：建 `Stack`（注入 `StackConfig.pts=PTSModeConfig(...)`，flags 来自命令行 `--pts-secure-pair-only` 等），建 `IutActions(stack)`，进 REPL。
- **不阻塞 event loop 读输入**：`line = await loop.run_in_executor(None, input, "pts> ")`，这样栈的异步事件（incoming connection、ATT 请求、SMP PDU）在等待输入期间照常被 event loop 处理。
- 命令语法（PRD §4.2）：

```text
advertise [--type=adv_ind|...] [--data=<hex>]
scan [--active]
connect <addr> [--classic]
disconnect [<handle>]
pair [--io-cap=<cap>] [--mitm]
encrypt [<handle>]
notify <char_handle> <hex> [<conn_handle>]
indicate <char_handle> <hex> [<conn_handle>]
read <char_handle> [<conn_handle>]
write <char_handle> <hex> [<conn_handle>]
sdp-browse <addr> [--uuid=<uuid>]
rfcomm-open <addr> <channel>
l2cap-connect <addr> <psm>
set-io-cap <NoInputNoOutput|DisplayOnly|DisplayYesNo|KeyboardOnly|KeyboardDisplay>
status
help
quit
```

- 解析：`shlex.split(line)` + 每命令一个小 handler，调对应 `IutActions` 方法，捕获异常打印 `error: ...`（REPL 不因单条命令失败退出）。
- 命令解析逻辑抽成 `parse_repl_command(line) -> (cmd, args)` 纯函数，可单测（不需真栈）。

## 6. PICS 半自动生成器

`pybluehost/pts/pics_gen.py` + CLI `pybluehost tools pics-gen`：

- **数据源**（全是已有的）：`cli/tools/info.py` 的 capability dump（Supported_Commands / LMP / LE features 解码）、`hci/features_decode.py` 的 feature 名表、各层 `__init__` 公共 API（哪些 profile/层实现了）、profile 注册信息。
- **输出**：每个 target test group 一份**结构化 PICS 草稿**（YAML/Markdown 表：feature 项 → supported yes/no + 来源依据），写到 `docs/pts/pics/<group>.draft.yaml`。
- **流程**：生成草稿 → **人工校正**（删除栈不真支持的、补 PTS 特有项）→ 操作员据此在 PTS UI 勾选（PTS 导入格式是专有 UI 操作，v1.2 不自动写 PTS 工程文件，只产人读草稿）。
- IXIT（`docs/pts/ixit/`）：手写（IUT 地址 / key 等测试参数），生成器不碰。
- 价值：栈加 feature 后可重生成草稿，PICS 与实际能力不脱节。
- 测试：用固定的 capability dump fixture（已有硬件 JSON：`docs/hardware/*.json`）→ 断言生成的 PICS 草稿含/不含特定 feature 项。

## 8. 错误处理

| 场景 | 行为 |
|---|---|
| REPL 单条命令参数错/栈调用失败 | 捕获，打印 `error: <msg>`，**REPL 继续**（不退出） |
| `handle` 省略但无 `last_handle` | `error: no active connection; specify <handle>` |
| PTS mode flag 组合非法（如 smp_options 与 secure_pair_only 冲突） | 建栈时 `_validate_sc_dependencies` 同款 `ConfigurationError`，CLI 报错退出 |
| PICS 生成数据源缺失（无 capability dump） | 生成器报清晰错误，提示先跑 `tools info` 或接硬件 |
| `quit` / EOF (Ctrl-D) | 干净关栈退出 |

## 9. 测试策略

**纯软件 / virtual（CI）：**
- PTS mode flags：loopback 两 `Stack.virtual()`，开各 flag 断言行为（secure-only 拒 legacy、smp_failure 发 Pairing Failed、smp_options 改配对包字节）；**关键回归**：`pts=None` 时跑现有 SMP 测试全绿（零影响证明）
- action layer：virtual stack，断言 advertise/connect/pair/notify/... 映射 + 会话状态
- REPL 解析：纯函数全命令覆盖
- PICS 生成器：硬件 JSON fixture → 草稿断言
- 验收门槛：全绿 + coverage 不低于现行 `--cov-fail-under`（85）

**真机 + PTS dongle 手动验收（记到 `docs/pts/results/`）：**
- 操作员用 `pybluehost app pts-iut -t usb --pts-...` 驱动，跑各 target group（HCI/L2CAP/GAP/GATT/SMP/SDP/RFCOMM）适用 test case
- 记录通过率 + 暴露的栈 bug（**不设 ≥90% 硬指标**，见 PRD §7）
- bug 归档 → 修复（P.4 开放式迭代）

## 11. Phase 2 — auto-pts BTP 自动化

> **范围**：去掉人工 MMI 应答，让 auto-pts 程序化驱动 PyBlueHost 跑完整 LE test case 集 + CI 集成。Phase 1 完成后自然延伸，单独排期。

### 11.1 架构

```
┌──── Windows ────────────────────────────┐    ┌──── IUT 侧（可同机或独立）────────────────┐
│                                          │    │                                         │
│  PTS.exe + dongle                        │    │  pybluehost app pts-tester (新 CLI 命令)     │
│      ▲                                   │    │   - 监听 TCP/UNIX socket                 │
│      │ PTSControl COM                    │    │   - 收 autoptsclient 来的 BTP 帧         │
│  autoptsserver  ◄──────XML-RPC──────────►│    │   - 分发到 BTP service handlers          │
│   (上游 auto-pts，不改)                   │    │       │                                 │
│      RunTestCase / 回调 MMI               │    │       ▼                                 │
└──────────────────────────────────────────┘    │  BtpService Handlers                   │
                                                 │   (Core / GAP / GATT / L2CAP / SMP)    │
        ┌─────────autoptsclient────────────┐    │       │ 调 Phase 1 的 IutActions       │
        │  projects/pybluehost/  (本子项新增)│    │       ▼                                 │
        │   - PICS / IXIT 模块               │    │  IutActions  (Phase 1，复用)           │
        │   - tester 启动/停止 hook         │◄──────────────┘                              │
        │   - WID handlers（多复用上游）      │     BTP over socket                          │
        │  + 上游 per-profile WID handlers   │    │       │                                 │
        │   (gap_wid_hdl / gatt_wid_hdl ...)│    │       ▼                                 │
        └──────────────────────────────────┘    │  PyBlueHost Stack (PTS mode flags 开)   │
                                                 └─────────────────────────────────────────┘
```

**两端复用**：
- **Phase 1 的 `IutActions`** 是 BTP service handlers 的下游——Phase 2 **不重写**驱动栈逻辑
- **PTS mode flags** 对两 Phase 通用（同一 StackConfig.pts）
- 与 Phase 1 唯一新增的"前端"层是 BTP 协议 + 网络监听

### 11.2 BTP 协议（auto-pts Bluetooth Test Protocol）

**帧格式**（5 字节 header + variable data，参见 auto-pts repo `doc/btp_*.txt`）：

```
+--------+--------+------------------+----------+---------+
| Service|Opcode  | Controller Index | Length        | Data  |
| ID (1B)| (1B)   | (1B)             | (2B, LE)      | (var) |
+--------+--------+------------------+----------+---------+
```

**Service ID 命名空间**（保留上游编号，**v1.2 实现 LE 子集**）：

| Service | 范围 | v1.2 Phase 2 |
|---|---|---|
| Core | 协议自身：Read Supported Commands/Services、Register/Unregister Service、Reset Board | ✅ 必做 |
| GAP | advertise/scan/connect/disconnect/pair/IO cap/passkey/bond | ✅ 必做 |
| GATT (含 ATT) | add service/characteristic/descriptor、set value、notify/indicate、discover/read/write | ✅ 必做 |
| L2CAP | connect/disconnect/send/listen on PSM | ✅ 必做 |
| SMP | 部分功能合在 GAP，独立 SMP 服务上游存在 | ✅ 必做（覆盖 SMP test group 所需的 opcode 子集） |
| MESH / VCS / MICS / HAS / CSIP / ... | LE Audio / Mesh | ❌ 不在 v1.2 范围 |

**Opcode 约定**：
- 命令 opcode：低位区（每 service 自己定义）
- **Status response**：opcode `0x00` + 1 字节 error code（每 service 统一）
- **Event**：opcode 高位置 1（≥ `0x80`），异步从 IUT → client

**具体 opcode 编号不在本 spec 重复**——以 auto-pts 上游 `doc/btp_core.txt` / `doc/btp_gap.txt` / `doc/btp_gatt.txt` / `doc/btp_l2cap.txt` 为权威；Plan P.6/P.7/P.8/P.9 各自落实时引用对应文件并加单测固化字节布局。

### 11.3 transport：socket vs UART

| 选项 | 取舍 |
|---|---|
| **TCP socket（推荐 v1.2）** | autoptsclient 默认支持；同机 / 跨机都灵活；零额外硬件 |
| UNIX domain socket | 同机更快但仅 Linux；auto-pts 上游有支持 |
| UART (serial) | 上游主要给 embedded IUT（Zephyr/Mynewt）用；PyBlueHost 是 Python 进程，无意义 |

**v1.2 Phase 2 走 TCP**：`pybluehost app pts-tester --listen=127.0.0.1:65103`（端口可改）。autoptsclient 的 `projects/pybluehost/` 配为 TCP 连接。

### 11.4 v1.2 Phase 2 范围 vs NON-Goal

**做**（与 Phase 1 的 7 个 target group 中的 LE 子集对齐）：

| target group | Phase 2 BTP 覆盖 |
|---|---|
| HCI | 通过 Core service 间接（Read Supported Commands 等） |
| L2CAP | LE CoC ✅ + Classic L2CAP 仅在 BTP 支持范围内 |
| GAP | ✅ 全 |
| GATT | ✅ 全 |
| SMP | ✅ 全 |
| **Classic SDP** | ❌ auto-pts BTP 历史上无 SDP service（上游 Zephyr/Mynewt LE-centric）→ **保留 Phase 1 REPL 手动** |
| **Classic RFCOMM** | ❌ 同上 → **保留 Phase 1 REPL 手动** |

**显式 NON-Goal**：
- Classic SDP/RFCOMM 自动化（Phase 1 REPL 兜底，未来 auto-pts 上游若加再支持）
- LE Audio / Mesh BTP service
- fork auto-pts（作为外部依赖 + 上游贡献 `projects/pybluehost/`）
- 改 autoptsserver / PTSControl COM 封装（上游直接用）
- 自己写 MMI 应答（复用上游 per-profile WID handlers）

### 11.6 与 Phase 1 接口的前向兼容性

`IutActions` 在 Phase 1 设计时**已经按"两个前端共用"原则**（spec §2/§4 已声明）：

| Phase 1 已落地 | Phase 2 复用 |
|---|---|
| `IutActions.advertise` / `scan` / `connect` / `pair` / `notify` / `indicate` / `read` / `write` / `l2cap_connect` 等原语 | BTP service handler 直接调（无须再加 method） |
| `ConnInfo` + `IutSession`（含 `gatt_client`） | BTP GATT client opcodes 用到（central 角色 read/write）；BTP GATT server opcodes 用 `stack.gatt_server` |
| `PTSModeConfig` | 同样适用 Phase 2 跑 PTS（test case 触发的特殊行为通过 flag 注入） |
| `on_connection_event` 自动登记 incoming 连接 | BTP GAP events（GAP_CONNECTED / GAP_DISCONNECTED）映射这条流 |

**唯一可能的回头修**：Phase 1 实施 `IutActions` 时若发现某动作返回值不便编 BTP 响应字节（如 `connect` 返回 GATTClient 对象 vs Phase 2 BTP 需要 conn handle 字节），P.5 会加薄 adapter 而不动 `IutActions` 签名。**Phase 1 不预先为 BTP 改动作签名**——保持原语对 REPL 自然，BTP adapter 自己 marshal。

### 11.7 测试策略（Phase 2）

**纯软件 / CI**：
- **BTP 协议编解码**：固定字节 fixture 断言 header + 各 service 代表性 opcode 的 encode/decode（参考上游 `doc/btp_*.txt`）
- **service handler**：fake `IutActions`（记录调用），断言 BTP 命令字节→正确 action 调用 + 正确 BTP 响应字节
- **BtpTester socket 集成**：本地起 server，asyncio client 发 BTP 命令断言响应（不需真栈，handler 层用 fake）
- **virtual e2e**（重）：起两个 `Stack.virtual()`，一个跑 BtpTester（IUT），另一个当对端；模拟 autoptsclient 发 BTP 命令完成完整 advertise→connect→pair→GATT 读写流程；断言 BTP 事件序列符合 spec
- **关键回归**：Phase 1 REPL 路径 + virtual e2e 在 Phase 2 完工后**仍全绿**（共享 `IutActions` 不能被 BTP 路径破坏）

**真机 + PTS dongle + 真 autoptsclient（手动 + 半自动）**：
- 跑 autoptsclient 对 PyBlueHost BTP tester 完整 LE test case 集
- 通过率 + 失败 case 归档；与 Phase 1 手动跑通的 group 通过率对比（应 ≥ Phase 1，新失败的是真 bug）
- CI 集成：autoptsclient 对 virtual transport 自测（无 PTS dongle，跑不到真 conformance，但 BTP↔IUT 链路常态自检）
